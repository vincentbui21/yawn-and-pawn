# Spike S3: House Hunt image matching

**Story:** 7.6 · **Refs:** FR-PWK-6, FR-PWK-11, NFR-4, AD-9, AD-15; PRD §10 S3, §12, Q10, Q11 · **Verify:** human-verify

> **House Hunt moved to v2 by owner decision 2026-10-27; this is input for v2.**
> Reasons: a false reject at 6 am leaves the user unable to stop the alarm; dim-morning photos can't be validated
> without real homes; the QR/Barcode check already covers "get up and go somewhere"; a faster launch.
> Stories 7.7, 7.8 and 7.9 are `deferred-v2` in `sprint-status.yaml`. House Hunt stays hidden from every check picker.

The spike was stopped by that decision before the accuracy evaluation ran. No prototype code was written and nothing was
added to the app or to `config/dependency-allowlist.txt`. What follows is what was measured before the stop (package
inspection, no photos), the plan the evaluation was going to follow, and the questions v2 must answer.

## What was measured (2026-10-27)

Candidate stack (Architecture Stack v0.3): MediaPipe `com.google.mediapipe:tasks-vision:1.0.0` `ImageEmbedder`, with a
MobileNet-V3 embedder model bundled in assets.

| Item | Measured | Source |
|---|---|---|
| `tasks-vision-1.0.0.aar` | 0.5 MB, Java only (no native code) | Google Maven |
| `tasks-core-1.0.0.aar` (pulled in by tasks-vision) | 22.5 MB AAR; native `libmediapipe_tasks_jni.so` per ABI: arm64-v8a 11.0 MB, armeabi-v7a 7.7 MB, x86_64 13.7 MB, x86 15.6 MB (uncompressed) | Google Maven |
| Model `mobilenet_v3_small` embedder (float32) | 4.1 MB | `storage.googleapis.com/mediapipe-models/image_embedder/...` |
| Model `mobilenet_v3_large` embedder (float32) | 10.9 MB | same |
| Extra runtime dependencies (tasks-core POM) | Flogger 0.6 (+ system backend), Guava 27.0.1-android, protobuf-javalite 4.26.1, datatransport `transport-api` / `transport-backend-cct` / `transport-runtime` | Maven POMs |

**Estimated install cost on an arm64 phone** (App Bundle split by ABI): about 11 MB of native code plus 4.1 MB (small)
or 10.9 MB (large) of model, so **roughly 15 to 22 MB uncompressed** on top of today's app. Download size is smaller
after compression, but this is far more than every other check together. v2 should weigh it against a lighter runtime
(LiteRT / TensorFlow Lite interpreter with the same `.tflite` model, or Play services LiteRT) before choosing MediaPipe.

### Network and data collection (AD-15): MediaPipe sends usage statistics

`tasks-core` 1.0.0 contains `com.google.mediapipe.tasks.core.logging.TasksStatsLoggerFactory`, which creates
`TasksStatsProtoLogger` (not the `TasksStatsDummyLogger` that is also in the jar). That logger sends
`MediaPipeLogExtension` events through `RemoteLoggingClient`, which uses Google's datatransport
`CCTDestination` (Clearcut) with log source `COREML_ON_DEVICE_SOLUTIONS`. In other words, **every task created would
report anonymous usage and performance events to Google over the network**, the same way ML Kit's `common` module
already does for the QR/Barcode check (declared in `config/dependency-allowlist.txt`).

The photos and embeddings themselves would never leave the phone (the logger carries task names, modes, timings and
error codes, not images). Still, for v2:

- this is a new data flow for the Epic 8 Data safety form ("App activity / diagnostics" style, collected by a Google
  SDK), unless it can be switched off;
- check whether MediaPipe offers a documented opt-out (an option or a manifest flag) or whether the LiteRT route avoids
  it entirely; record the answer here before adding the dependency.

## Evaluation plan (not run)

The plan below follows the story's acceptance criteria and is ready to run in v2. The harness and the photo set never
go to `main` (spike branch only), and only aggregate numbers come back into this file.

1. **Models:** MobileNet-V3 small and large embedders, float32, loaded from a local file (no network), cosine
   similarity on L2-normalised embeddings. The desktop `mediapipe` 1.0.0 Python wheel runs the same task graph and model
   as Android, so desktop numbers for accuracy carry over; timings do not.
2. **Genuine photos:** at least 10 spots in at least 3 homes, 3 reference photos each, test photos under daylight, lamp
   light and dim morning light, at the same angle, ±15° and ±30°, and with small changes (a towel moved, a hand in
   frame). Score = best similarity against the 3 references.
3. **Impostors:** other spots in the same room, other rooms, random photos, and the reference photo shown on a second
   phone and printed on paper (reported on its own; PRD Q11).
4. **Report per model:** false-reject and false-accept rates for thresholds 0.50 to 0.95 in 0.05 steps, embedding time
   and memory on the budget device (Oppo A96) and a Pixel, and model size.
5. **Targets (owner default 2026-09-26):** false rejects ≤ 10% per attempt, false accepts for other rooms and random
   photos ≤ 1%, match time ≤ 500 ms on the budget device.

A desktop-only run on public multi-view sets (for example HPatches viewpoint and lighting sequences, plus indoor scene
photos with synthetic viewpoint, lighting, blur and occlusion changes) can screen the models and pick a threshold range
cheaply, but it cannot replace real homes: public sets are mostly planar or outdoor, and synthetic dimming does not
reproduce a phone camera's noise and auto-exposure at 6 am. That gap is one of the reasons for the v2 decision.

## Open questions for v2

1. **False rejects are the dangerous error.** A reject at 6 am means the alarm cannot be stopped except through the
   fallback link after 5 failed attempts (FR-PWK-11). v2 should decide whether House Hunt offers the fallback sooner
   (for example after 2 to 3 rejects) or shows the reference photo larger to help re-framing.
2. **Dim morning light** is the condition most likely to fail and the hardest to test without real homes. Does the
   torch help or hurt (glare on tiles and mirrors)?
3. **Runtime choice:** MediaPipe tasks (simple API, about 11 MB native code on arm64, Clearcut usage logging) or the
   LiteRT interpreter with the same model (smaller, no logging found yet; preprocessing written by hand).
4. **Model choice:** small (4.1 MB) unless large clearly lowers false rejects at the same false-accept rate.
5. **Photo of a photo** (PRD Q11): expected to pass at most thresholds. Accept it as a known limitation, as planned.
6. **Thresholds per difficulty** (Easy, Medium, Hard) as core config values, the number of reference photos (1 to 3),
   and 1 spot per check (PRD Q10).

## What a real-phone test must check (v2, the Story 7.12 House Hunt items)

Record pass/fail, device, Android version and date for each:

1. Embedding time for one 1024 px photo on the Oppo A96 (target ≤ 500 ms including decode), first call (model load)
   and later calls, and peak memory.
2. Install size change of the APK / App Bundle download with the chosen runtime and model.
3. With network logging visible (for example a proxy or `adb shell dumpsys` of the datatransport job), whether any
   request is sent when the matcher runs; confirm with airplane mode that matching works fully offline.
4. Same spot, same angle, daylight / lamp / dim morning: similarity values and accept or reject at the chosen threshold.
5. Same spot at about ±15° and ±30°, and from one step to the side: accept or reject.
6. Same spot with a towel moved and a hand in frame: accept or reject.
7. Another spot in the same room, another room, and a random photo: always reject.
8. The reference photo shown on a second phone and printed on paper: record the result (known limitation).
9. A covered camera and a revoked camera permission: the fallback appears as the story requires.

## Decision

**No-go for v1 by owner decision 2026-10-27** (scope, not measured accuracy). House Hunt (FR-PWK-6) moves to v2; Stories
7.7 to 7.9 are deferred to v2 and House Hunt stays hidden from check pickers. The House Hunt preview screens from design
round 3 and the existing `HouseHuntRegistration` composable stay in the codebase for v2. No MediaPipe dependency, model
or permission was added.
